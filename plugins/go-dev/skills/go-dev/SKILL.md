# Go Development Policy (`go-dev`)

## General Principles

* **Package Cohesion**: Packages should be small, focused, and adhere strictly to the Single Responsibility Principle.
* **Testing**: All packages must contain corresponding unit test files suffixed with `*_test.go`.
* **Error Handling**: Standard Go error handling must be used, prioritizing wrapping (`%w`), checking (`errors.Is/As`), and explicitly avoiding ignored errors (`_`).
* **Context**: `context.Context` must be the first parameter in function signatures and must not be stored as a field.
* **Concurrency**: Goroutine ownership and shutdown must be clearly defined. Resources must be released deterministically (e.g., using `defer`).
* **Typing**: Favor concrete types and small, consumer-defined interfaces over excessive use of empty interfaces.
* **Generated Files**: No manual edits are permitted on code generated by tools (e.g., protobufs, mocks).
* **API Stability**: Preserve exported APIs unless a specific change has been authorized and documented.
* **Interfaces**: Define interfaces in the place of use, not near the structure definition.
* **Comments**: Do not add comments unless it's inevitable for describing external world effects.

## Mandatory Core Pipeline

When changes are made to Go modules, the following pipeline must be executed:

1. Run `gofmt -w` on all changed, non-generated Go files to ensure consistent formatting.
2. Run `go mod tidy` only if the changes involved imports, module definitions, or external dependencies.
3. Run `go vet ./...` to perform static analysis and check for suspicious constructs.
4. Run the configured repository linter, if one is defined for the Go language.
5. Run `go test -count=1 ./...` for basic unit test execution.
6. Run `golangci-lint --timeout 3m run ./...  --fix` to find the issues. Fix all the issues found. Do not use any `nolint`, fix issues, not hide them.

**State Management**: If steps 1, 2, or 3 result in changed files (i.e., formatting or fixes were applied), the restart analysis and/or tests must be re-run.

## Test Configuration

Tests tagged with `-race`, coverage checks, `govulncheck`, generator, tagged, integration, or fuzz must be defined as conditional tests, managed by the repository configuration or CI pipeline, not mandated by this skill.
